# v3: один бэкенд на Rust — решение и план миграции

Статус: прототип ядра собран в ветке `v3-rust-core`; v2 заморожен.
Дата: 2026-11-26.

## 1. Вопрос

Стоит ли переносить v3 на Rust, и лучше ли это Java, C# или C++ по четырём
критериям:

1. чистота кода и модели;
2. стабильность сборки и поведения;
3. детерминированность;
4. многопоточность.

Дополнительное условие: весь бэкенд (не только вычислительное ядро, но и
классы автоматов, расписание, ротация, логирование) должен быть на одном
языке. Python остаётся для аналитики, графиков и Telegram-бота.

## 2. Решение

**Rust — основной вариант для v3.** Это не потому, что Rust быстрее всех
(разница с C++/C# на такой задаче вторична), а потому что он лучше всех
совмещает контроль за состоянием, отсутствие GC и безопасную многопоточность
при переносе всего бэкенда на один язык.

Ключевая оговорка: **детерминированность в Rust не появляется автоматически**.
Её обеспечивают конкретные решения: один RNG на мир, явный порядок обхода,
отсутствие `HashMap` в горячем пути, отсутствие межпоточных reduce по
floating point и фиксированные правила округления. Rust лишь делает нарушения
видимыми на этапе компиляции (владелец, `Send`/`Sync`, отсутствие скрытого
общего изменяемого состояния).

Если приоритетом окажется скорость разработки, а не долгосрочная чистота,
второй кандидат — **C#**. Java — третий: язык слабее выражает предметную
модель, а JVM/GC добавляют скрытое состояние. C++ для переписывания с нуля
не рекомендуется: он даёт максимум контроля, но именно по чистоте и
стабильности проигрывает трём остальным.

## 3. Сравнение

| Критерий | Rust | C# | Java | C++ |
|---|---|---|---|---|
| Чистота модели | enum + pattern matching, нет null, модули, явные типы | сильный ООП, records, но GC и много церемоний | сильный, но многословный, примитивы/объекты | мощный, но UB, макросы, legacy-приёмы |
| Стабильность | нет GC, cargo.lock, стабильные editions | LTS, GC, стабильный runtime | LTS, GC, стабильный runtime | ABI, компиляторы, UB, сборочные системы |
| Детерминизм | контракт проектируется; `f32` явный; нет скрытого состояния | JIT/GC, нужна дисциплина; FMA/оптимизации | `strictfp`, но GC и `HashMap` | нужна дисциплина; `-ffast-math` и UB опасны |
| Многопоточность | compile-time `Send`/`Sync`, scoped threads | хорошая, но гонки ловятся в рантайме | хорошая, но гонки ловятся в рантайме | ручная, гонки = UB |
| Экосистема | cargo; ClickHouse/графики слабее | очень сильная | очень сильная | зрелая, но разрозненная |
| Скорость разработки | средняя/низкая (borrow checker) | высокая | высокая | низкая/средняя |
| Один язык для бэкенда | ядро + CLI + I/O без Python | да | да | да, но ценой сложности |
| Runtime | нативный бинарник | .NET | JVM | нативный бинарник |

### Почему не «просто остаться на C++»

Текущая v2 работает, но главный источник расхождений — не C++ сам по себе, а
разделение семантики между Python и C++: выбор цели, отказ, реакции и
затухание живут в C++, а расписание, логирование и часть реакций — в Python.
Перенос v3 на один язык устраняет этот класс ошибок. Если переносить всё на
C++, сложность ручного управления памятью и потоками сохранится, а
читаемость не улучшится.

### Почему не Java/C#

Оба варианта жизнеспособны. C# даже удобнее для быстрого прототипа:
структуры, `Span<T>`, `Parallel.For`, хороший HTTP-клиент и официальный
ClickHouse-драйвер. Но:

- GC добавляет непредсказуемые паузы и скрытое разделяемое состояние;
- для плотной матрицы отношений 1620×1620 нужны primitive-массивы, а не
  объекты, и дисциплина в C#/Java всё равно ручная;
- гонки данных в обоих языках ловятся только в рантайме, тогда как Rust
  запрещает их на этапе компиляции;
- JIT-поведение и оптимизации усложняют воспроизводимость траектории между
  машинами.

Для CRUD-сервиса или веб-бэкенда Java/C# были бы лучше. Для длинной
детерминированной симуляции с плотными числовыми массивами Rust выигрывает.

### Где Rust проигрывает

- borrow checker замедляет итерации, особенно при обновлении графа связей;
- экосистема ClickHouse и графиков слабее, чем в Python/Java/C#;
- компиляция заметно медленнее;
- меньше людей, знакомых с языком;
- для быстрого researc-прототипа Python всё ещё удобнее.

Поэтому архитектура v3 сознательно разделяет **вычислительное ядро** и
**аналитику**: ядро и университетская логика — Rust, pandas/matplotlib и
Telegram — Python.

## 4. Архитектура одного бэкенда

```
rust/
  crates/
    automata-core/        # домен: агенты, архетипы, эмоции, отношения,
                          # исходы, RNG, фазы дня; без I/O и зависимостей
    automata-university/  # календарь, группы, посадка, спортзал, ротация
    automata-io/          # CSV/ClickHouse HTTP, манифест прогона, тайминги
    automata-web/         # HTTP/JSON API, SSE/WebSocket, раздача web/dist
    automata-cli/         # сценарный раннер и batch/resume
web/                      # веб-фронтенд (SPA), собирается в web/dist
python/
  scripts/                # аналитика, отчёты, графики
  core/                   # Telegram-бот и аналитические обёртки
```

Правила:

- `automata-core` не знает про ClickHouse, файлы, Python и Telegram;
- `automata-university` знает про календарь и университет, но не про базу;
- `automata-io` — единственное место, где есть I/O с базой и файлами;
- `automata-web` — только API и раздача статики, без логики симуляции;
- `automata-cli` собирает сценарий из конфигурации и вызывает фазы;
- веб-фронтенд ничего не считает сам, он показывает состояние и отчёты;
- Python-аналитика читает те же таблицы и не влияет на симуляцию.

Такое разделение позволяет тестировать ядро без базы и переиспользовать его
в разных мирах (университет, квартира) без ветвлений в горячем цикле.

### 4.1. Веб-фронтенд

Фронтенд — обычное веб-приложение, а не десктоп и не TUI.  Предлагаемый
стек: **TypeScript + React + Vite**, графики — ECharts или Chart.js,
сборка в статический `web/dist`, который раздаёт `automata-web`.  Если
хочется избежать Node-тулчейна, тот же API можно обслуживать статическими
ES-модулями, но React/Vite дают более предсказуемую структуру для
дипломного проекта.

Минимальный API:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | живость сервиса |
| `GET` | `/api/runs` | список прогонов, статусы, прогресс |
| `GET` | `/api/runs/{id}` | манифест, тайминги, текущий день |
| `GET` | `/api/runs/{id}/reports` | ссылки на отчёты и графики |
| `POST` | `/api/runs` | запуск сценария |
| `POST` | `/api/runs/{id}/stop` | мягкая остановка |
| `GET` | `/api/events` | SSE: прогресс, новые строки лога |
| `GET` | `/plots/*` | статические PNG из `data/plots` |

Правила:

- веб-слой не держит состояние симуляции в памяти: источник истины —
  ClickHouse/манифест, а веб только читает и отправляет команды;
- долгие прогоны выполняет `automata-cli`/systemd, а не HTTP-обработчик;
- по умолчанию сервис слушает `127.0.0.1`, доступ снаружи — через reverse
  proxy и токен из окружения;
- фронтенд не влияет на детерминизм: он не может менять параметры уже
  запущенного прогона;
- Telegram-бот остаётся, но становится вторым клиентом того же состояния.

Интерфейс: матрица 18/54 сценариев, прогресс по дням, тайминги, отчёты
H1–H18, графики и хвост лога.  Этого достаточно для защиты и для
повседневного мониторинга; сложный редактор сценариев не нужен.

## 5. Что уже перенесено

- 9 архетипов с исправленными параметрами v2;

- дневное затухание отношений, реакцию отношений на эмоции, затухание
  эмоций, реакцию эмоций на отношения;

- детерминированный хеш состояния и CLI с key=value/CSV.

  внешний добор, перевод M1 → M2, повышение курсов, выпуск;

  коридор на 1500 и спортзал на 1000 мест; 6 колонок в аудиториях и 42 в
  коридоре/спортзале, три изолированные секции спортзала;

  15%, спортзал 10%, остальное — семинары; отдельные генераторы для
  начальных и пост-ротационных когорт;

- девятислотовый день `PAIR_1, BREAK_1, PAIR_2, BREAK_2, PAIR_3, BREAK_3,
  PAIR_4, GYM, CLEANUP`, пропуски, уход с кампуса, коридор и спортзал;

  STOP с весом среднего, клика внутри группы;
- воскресный сдвиг `randint(-30, 30)` на все семь осей плюс затухание
  эмоций; семестровый сброс эмоций; обслуживание отношений/эмоций один раз

Тесты: 27 core + 43 university unit + 3 integration; полный университетский
прогон проверяется отдельным `--ignored` тестом в release. `cargo clippy
--workspace --all-targets -- -D warnings` и `cargo fmt --check` проходят.
Набор проверен на Rust 1.99.1 и 1.100.0; ядро не имеет внешних зависимостей.

## 6. Семантика, которую фиксирует v3

Это правила, которые нельзя «потерять» при переносе:

1. Внутренняя шкала — целые x10; на границах (лог, отчёт) делится на 10.
2. Отказ определяет цель, а не инициатор; отказ контекстно-зависим.
3. При состоявшемся контакте успех и неудача равновероятны (50/50) после
   разрешения отказа.
4. `sigma=+1` ускоряет рост на положительной полуоси и замедляет на
   отрицательной; `sigma=-1` — наоборот; ноль относится к положительной
   полуоси.
5. Отказ штрафует все три функции у обоих участников; главная ось архетипа
   получает полный вес, остальные — половинный.
6. Эмоциональная реакция использует снимок `E(t)` обоих участников; скорость
   0.15, множитель веса архетипа `weights/10`.
7. Обновление отношений: база 15 (affinity) и 10 (trust), множитель эмоции
   партнёра 2.0 / 0.5, усечение к нулю.
8. Порядок дня: затухание отношений → реакция эмоций на отношения →
   затухание эмоций → реакция отношений на эмоции → влияние → контакты.
9. Затухание эмоций `d_E=2`; затухание отношений: положительная полуось
   0.5 шага, отрицательная — 1.0.
10. Влияние: top-8 по модулю среднего отношения, вес `(|mean|+20)/100`,
    доминирующая ось партнёра весит больше, шаг `min(0.9, 0.6*sensitivity)`.
11. Классификация отношений — постфактум, на управление не влияет.
12. `emission_weights` в v2 в проде не задаются (остаются нулями), поэтому
    соответствующий член в v3 не переносится. Если v3 даст им смысл, это
    будет отдельное явное поле, а не скрытая случайность.

Где Python и C++ v2 расходились, v3 выбирает один вариант и документирует
его. Например, контекст в отказе и эмоциональных реакциях берётся из Python
(в C++ отказ контекст не учитывал), а округление — усечение к нулю, как в
`int(value + delta)` Python и `(int)` C++.

### 6.1. Календарь: исправление, а не перенос ошибки

При переносе календаря обнаружено расхождение между предположением
аналитики и фактическими данными v2. В v2 `day_id` — это плотный номер
*смоделированного* дня. Летние месяцы (июль и август) не моделируются:
после 30 июня дата сразу прыгает на 1 сентября. Поэтому `day_id % 7`
совпадает с днём недели только в первом учебном году. Дальше воскресенья
сдвигаются: в данных v2 пропущенные дни имеют остатки 0, 1, 2, 3 по модулю
7 в разных учебных годах, а не только 0.

Проверка по `agent_states` одного прогона: 1041 различный день из 1213,
172 пропуска; это 173 воскресенья минус день 0, который логируется как
начальное состояние до первого воскресного сброса. По учебным годам
воскресений 44 + 43 + 43 + 43.

v3 **не воспроизводит эту ошибку**. В календаре есть явные `date` и
`weekday`; аналитика не должна выводить день недели из `day_id % 7`.
`day_id` остаётся плотным 0..1212, а `CalendarDay::is_sunday` вычисляется по
настоящей дате. Тест `summer_drift_is_explicit_and_not_hidden_in_day_id`
фиксирует это поведение.

## 7. Контракт детерминизма

1. Один `SplitMix64` на мир, seed задаётся в манифесте.
2. Никакого `thread_rng`, `RandomState`, времени или адресов памяти в модели.
3. Обход — по плотным индексам; карты — `BTreeMap`; `HashMap` запрещён в
   горячем пути.
4. Параллельные фазы не делают общий reduce по `f32`; каждый поток пишет
   только свой срез, результат не зависит от числа потоков.
5. Число потоков — параметр производительности, а не семантики. Тест
   `determinism.rs` сравнивает хеш состояния, состояние RNG и счётчики
   контактов для 1/2/8 потоков.
6. Для сравнения с v2 используется не побитовая траектория, а агрегаты:
   распределения эмоций, доля отказов, структура связей, H1–H18.

## 8. Измерения прототипа

Замеры на Apple M-серии, release, один процесс:

| Сценарий | Потоки | sim_ms | Хеш |
|---|---:|---:|---|
| 100 агентов, 30 дней, mixed | 1 | 5.1 | `0x5fc52219d097ca7b` |
| 100 агентов, 30 дней, mixed | 2 | 7.3 | тот же |
| 100 агентов, 30 дней, mixed | 8 | 17.7 | тот же |
| 1620 агентов, 5 дней, empty | 1 | 176.9 | `0x5382a798416ca540` |
| 1620 агентов, 5 дней, empty | 2 | 160.8 | тот же |
| 1620 агентов, 5 дней, empty | 8 | 152.7 | тот же |
| университет, 1213 дней, 1620, mixed | 1 | 25 900 | `0x79f5809385358043` |
| университет, 1213 дней, 1620, mixed | 8 | 12 900 | тот же |

Вывод: хеш не зависит от потоков; ускорение на 1620 агентах умеренное
(1.2× на 8 потоках), потому что последовательный выбор цели и память
доминируют. Это ожидаемо для generic-прототипа «все против всех». В
университетском мире кандидаты ограничены аудиторией/секцией, а тяжёлые
дневные фазы распараллеливаются, поэтому полный прогон укладывается в
26–31 с на одном потоке и около 13 с на восьми.

Полный университетский прогон `seed=42`, `mixed`, 1213 дней даёт
4 294 325 контактов (1 537 291 успех, 1 538 053 неудачи, 1 218 981 отказ),
173 воскресенья, 3 академические ротации и 1620 студентов в конце
(1500 бакалавров + 120 магистров). Это ~4130 контактов на учебный день,
что совпадает по порядку с v2 (около 4150).

| 5 | Веб: `automata-web` API + SPA-дашборд, SSE-прогресс, отчёты и графики | 1–2 недели |
| 6 | Parity: прогон 18/54 сценариев, сравнение агрегатов с v2, проверка 1/2/8 потоков | 1–2 недели |
| 7 | Полные прогоны v3, аналитика остаётся Python | 1 неделя |

Итого: 6–9 недель одного разработчика при аккуратной работе. Если срок
защиты жёсткий, безопаснее оставить v2 на C++ и использовать Rust только
для исследовательского v3, не переводя весь бэкенд.

## 10. Риски и смягчение

- **Borrow checker и граф связей.** Решение: плоские массивы
  `relations[i*n+j]`, фазовый дизайн, снимки только там, где нужен
  read-after-write. Прототип уже показывает, что этого достаточно.
- **ClickHouse.** На сервере crates.io был недоступен. Решение: ядро без
  зависимостей; для вставок — HTTP-интерфейс ClickHouse на localhost или
  минимальный клиент. Драйвер добавляется только если сеть починится.
- **Графики.** `matplotlib`/`pandas` остаются в Python; это не недостаток,
  а граница ответственности.
- **Паритет с v2.** Побитового совпадения не будет из-за другого RNG и
  порядка операций. Сравниваем агрегаты и проверяем, что выводы H1–H18 не
  меняются качественно.
- **Сроки.** Полный перенос — это переписывание, а не рефакторинг. Если
  сроки поджимают, v3 остаётся прототипом, а защита идёт на v2.

## 11. Итоговая рекомендация

- Для **v3 и одного бэкенда** — Rust, при условии, что есть 5–8 недель и
  готовность к более медленным итерациям.
- Для **максимальной скорости разработки** — C#; для **Java-стека** — Java;
  оба требуют ручной дисциплины по массивам, потокам и детерминизму.
- Для **сохранения текущего кода** — C++ v2 без переписывания, с тестами и
  санитайзерами; но это не решает проблему разделения семантики Python/C++.
- C++ как язык нового бэкенда не рекомендуется: выигрыш в контроле не
  компенсирует риск UB и сложность многопоточности.
